Domain terms in **bold** are defined in [GLOSSARY.md](../../GLOSSARY.md). The product contract is [docs/SPEC.md](../../docs/SPEC.md) ("Shopping List", "Screens → Lista zakupów"). This feature builds on [feature 001](../001-shell-products-dishes/spec.md) (Products) and [feature 002](../002-week-planning/spec.md) (Meals, Servings scaling, Linked and Detached Meals, copying to the next Week). It replaces the placeholder in the Lista zakupów tab.

## Background

The app's first purpose is to let one person shop once a week and buy exactly what the plan needs. The planned **Week** already holds every **Meal** with its **Servings**. This feature turns that plan into the **Shopping List**: one line per **Product** with the total amount to buy. The user can correct a line for what is already at home (an **Adjustment**), add things the plan doesn't know about (an **Extra**), tick lines off in the shop, and share the list as text.

The list is never generated by hand. It is always the current plan, with the Week's Adjustments, Extras and checks applied on top.

Words used in this spec (UI terms, not domain terms):

- **List item**: one line of the Shopping List. It is either a **Product item** (from the plan, an Adjustment, or both) or an **Extra**.
- **Planned amount**: the sum, over all Meals of the Week, of that Product's scaled Ingredient amount (`ingredient.amount / servingsYield × servings`, from the Meal's Dish or, for a Detached Meal, from its own copy).
- **Total**: Planned amount plus the Adjustment, if any. This is the amount to buy.
- **Shown Week**: the Week the Lista zakupów tab is showing.

## Clarifications

### Session 2026-11-17

- Q: Which Week does Lista zakupów show, and how does the user change it? → A: The list has its own Week navigation (← / → and a swipe) and opens on the current Week. It does not follow the Week viewed in Tydzień.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See what to buy for the Week (Priority: P1)

The user opens the **Lista zakupów** tab and sees every Product the Week's Meals need, once each, with the total amount in the Product's unit. Amounts read the way a shop sells them: 1500 g shows as 1,5 kg, and pieces are rounded up to whole numbers. When the user changes the plan in Tydzień, the list follows without any action on their part.

**Why this priority**: This is the reason the app exists. The other stories correct, tick off or share this list, and none of them is useful without it.

**Independent Test**: Plan a Week with a few Dishes that share Products (one Dish in two Meals, one Meal at 1,5 Servings, one Detached Meal with a changed amount), open Lista zakupów, and confirm every amount equals a hand calculation. Then change a Meal's Servings in Tydzień and confirm the list shows the new amount.

**Acceptance Scenarios**:

1. **Given** Dish "Owsianka" yields 2 Servings with 100 g "płatki owsiane" and 300 ml "mleko", and the Week holds "Owsianka" at 1 Serving on Monday and at 3 Servings on Wednesday, **When** the user opens Lista zakupów, **Then** it shows "mleko 600 ml" and "płatki owsiane 200 g", each once.
2. **Given** the same Week with a second Dish that uses 500 ml "mleko", **When** the user opens the list, **Then** "mleko" shows once, as "1,1 l".
3. **Given** Meals that need 2,5 pcs "jajka" in total, **When** the user opens the list, **Then** it shows "jajka 3 szt.".
4. **Given** a Detached Meal whose copy uses 80 g "płatki owsiane" per Serving where its Dish uses 50 g, **When** the user opens the list, **Then** that Meal adds its own 80 g per Serving, not the Dish's 50 g.
5. **Given** a Meal whose Dish has since become an **Archived Dish**, **When** the user opens the list, **Then** that Meal's Ingredients are still counted.
6. **Given** the list is open on the Shown Week, **When** the user goes to Tydzień, sets a Meal of that Week from 1 to 2 Servings and comes back, **Then** that Meal's Products show the higher amounts.
7. **Given** Products "cebula", "Awokado", "łosoś" and "ziemniaki" on the list, **When** the user opens the list, **Then** they appear as "Awokado", "cebula", "łosoś", "ziemniaki" (alphabetical, ignoring case, with Polish letters in their Polish places).
8. **Given** a Week with no Meals and no Extras, **When** the user opens the list, **Then** it shows a short message that there is nothing to buy for this Week yet.
9. **Given** today is Tuesday 2026-11-17, **When** the user opens the app and goes to Lista zakupów, **Then** it shows the list for "16–22 lis 2026", whatever Week Tydzień is showing.
10. **Given** the list for 16–22 lis 2026, **When** the user taps → or swipes the Week header to the left, **Then** the list for "23–29 lis 2026" is shown. ← or a swipe to the right goes back a Week.
11. **Given** Tydzień shows 30 lis – 6 gru 2026 and Lista zakupów shows 23–29 lis 2026, **When** the user switches between the two tabs, **Then** each keeps its own Week.

### User Story 2 - Tick items off while shopping (Priority: P1)

In the shop the user ticks each List item as it goes into the basket. Ticked items move to the bottom, so what is still to buy stays at the top. Ticks belong to that Week and survive closing the app.

**Why this priority**: The list is used in the shop, one-handed, often offline. Without ticks the user has to remember what is already in the basket, which defeats the purpose of one planned trip.

**Independent Test**: Tick three items on a list of ten, close and reopen the app offline, and confirm the same three are ticked and sit at the bottom. Then change the plan and confirm the ticks are still there.

**Acceptance Scenarios**:

1. **Given** a list with "cebula", "mleko" and "ziemniaki", **When** the user ticks "cebula", **Then** "cebula" is shown as ticked and moves below "mleko" and "ziemniaki".
2. **Given** "cebula" is ticked, **When** the user unticks it, **Then** it returns to its alphabetical place among the unticked items.
3. **Given** several ticked items, **When** the user views the list, **Then** the ticked items are alphabetical among themselves, below all unticked items.
4. **Given** ticked items, **When** the user closes the app and opens it again with no network, **Then** the same items are ticked.
5. **Given** "mleko" is ticked, **When** the user adds a Meal that also uses "mleko", **Then** "mleko" shows the new Total and stays ticked.
6. **Given** "mleko" is ticked in one Week, **When** the user views the next Week's list, **Then** "mleko" is not ticked there.

### User Story 3 - Correct an item for what is already at home (Priority: P2)

The user has half a bag of rice at home, so they tap "ryż" and enter −500 g. The line now shows what they still need to buy. If the correction takes the Total to zero or below, the line stays on the list, struck through, so the user can see it and undo the correction later.

**Why this priority**: Buying exactly what is needed means accounting for the pantry. The list is still usable without this (the user can skip a line mentally), so it ranks below seeing and ticking.

**Independent Test**: Plan a Week that needs 1 kg "ryż", add an Adjustment of −500 g, and confirm the line shows 500 g. Change the Adjustment to −1000 g and confirm the line is struck through but still listed. Remove the Adjustment and confirm the line shows 1 kg again.

**Acceptance Scenarios**:

1. **Given** the list shows "ryż 1 kg", **When** the user taps the line (not its tick), **Then** a sheet opens showing "ryż", the Planned amount (1 kg) and a field for the Adjustment in grams.
2. **Given** that sheet, **When** the user enters −500 and saves, **Then** the line shows "ryż 500 g" and also shows the Adjustment (−500 g), so the user can tell it differs from the plan.
3. **Given** "ryż" with an Adjustment of −500 g, **When** the user opens its sheet, **Then** the field shows −500, and entering a new value replaces it (Adjustments do not add up).
4. **Given** "ryż" needs 1 kg, **When** the user sets the Adjustment to −1000 g or −1200 g, **Then** the line stays on the list, struck through, with its Adjustment visible.
5. **Given** a struck-through "ryż", **When** the user clears the Adjustment (empty field or 0) and saves, **Then** the line shows "ryż 1 kg" and is no longer struck through.
6. **Given** "jajka" planned at 4,5 pcs, **When** the user adds an Adjustment of −2 pcs, **Then** the line shows "jajka 3 szt." (2,5 rounded up after the Adjustment).
7. **Given** "ryż" has an Adjustment of −500 g, **When** the plan grows to need 1,5 kg, **Then** the line shows "ryż 1 kg" and the Adjustment is kept.
8. **Given** "ryż" has an Adjustment of +200 g and the user then removes every Meal that uses "ryż", **When** the user views the list, **Then** "ryż 200 g" is still listed, so the Adjustment can be seen and cleared.
9. **Given** the Adjustment sheet, **When** the user enters text that is not a number, **Then** saving is blocked and the field is pointed out.

### User Story 4 - Add things the plan doesn't cover (Priority: P2)

The user also needs toilet paper and coffee, which no Dish uses. They type "papier toaletowy" into the list and it appears as an **Extra**: just the text, with no amount or unit. Extras are ticked like any other item and belong to that Week.

**Why this priority**: One trip a week only works if the list holds everything to buy, not just food from the plan. It is independent of Adjustments and ranks with them.

**Independent Test**: Add two Extras, tick one, change the plan, close and reopen the app, and confirm both Extras are there with the same tick state. Delete one and confirm it is gone.

**Acceptance Scenarios**:

1. **Given** the list, **When** the user types "papier toaletowy" in the field for new Extras and confirms, **Then** "papier toaletowy" appears on the list in its alphabetical place, with no amount, and the field is empty again.
2. **Given** the field for new Extras, **When** the user confirms it empty or with only spaces, **Then** nothing is added.
3. **Given** an Extra "kawa", **When** the user ticks it, **Then** it moves to the ticked part of the list like a Product item.
4. **Given** an Extra "kawa", **When** the user deletes it, **Then** it disappears from the list at once, without a confirmation.
5. **Given** an Extra "kawa" in one Week, **When** the user views another Week's list, **Then** "kawa" is not on it.
6. **Given** Extras in the Shown Week, **When** the user changes the plan or copies the previous Week into it with "Skopiuj do następnego tygodnia", **Then** the Extras are unchanged.

---

### User Story 5 - Share the list (Priority: P3)

The user taps "Udostępnij listę" and sends the list as plain text, e.g. to the other person in the household, who adds the lines to their own list by hand. Where the device can't share, the text is copied to the clipboard instead.

**Why this priority**: Two people use two separate installs (single-user app), so sharing text is the only way to merge their lists. It is useful, but the list works for one person without it.

**Independent Test**: With a list of Product items (one ticked, one struck through) and an Extra, tap "Udostępnij listę", send the text to a notes app, and confirm it contains the Week's dates and the expected lines with readable amounts. On a browser without sharing, confirm the same text is in the clipboard and a short message says so.

**Acceptance Scenarios**:

1. **Given** a list for 16–22 lis 2026, **When** the user taps "Udostępnij listę" on a device that can share, **Then** the system share sheet opens with plain text starting with a heading naming the list and the Week's dates, followed by one line per List item.
2. **Given** the shared text, **When** the user reads it, **Then** each Product item reads as its name and its Total in the same units as on screen (e.g. "mleko 1,1 l", "jajka 3 szt."), and each Extra as its text.
3. **Given** the list has ticked items and struck-through items, **When** the user shares it, **Then** the text holds only what is still to buy: unticked Product items with a Total above zero and unticked Extras. Ticked and struck-through items are left out.
4. **Given** a browser that cannot share, **When** the user taps "Udostępnij listę", **Then** the same text is copied to the clipboard and a short message confirms it.
5. **Given** the user cancels the system share sheet, **When** it closes, **Then** nothing changes and no error is shown.
6. **Given** a Week with nothing left to buy (no items, or every item ticked or struck through), **When** the user views the list, **Then** "Udostępnij listę" is not offered.

### Edge Cases

- **Same Product in many Meals and Dishes**: it is one line with the summed amount, however many Meals, Dishes or Detached copies it comes from.
- **Rounding of the Total**: the Total is computed from unrounded Meal amounts and rounded once, for display. Grams and millilitres show as whole numbers below 1000 (74,6 g → 75 g). From 1000 up they show as kg or l with up to 2 decimals and no trailing zeros (1250 g → 1,25 kg; 2000 g → 2 kg; 1234 g → 1,23 kg). Pieces are rounded up to a whole number after the Adjustment (2,01 → 3).
- **Near the 1000 boundary**: the unit switches on the rounded value, so 999,6 g shows as "1 kg", not "1000 g".
- **Tiny remainders**: a Total that is above zero but shows as "0 g" after rounding (e.g. 0,3 g) is shown as "1 g" so a needed item never reads as zero. A Total of zero or below is struck through instead.
- **Total exactly zero**: struck through, like a negative Total (docs/SPEC.md: "≤ 0").
- **Product renamed**: the line shows the new name at once and keeps its Adjustment and tick.
- **Products merged** (Produkty): the merged Product's line joins the kept Product's line. In each Week, the two Adjustments are added together, and the joined line is ticked only if both lines were ticked, so nothing still to buy is hidden.
- **Product deleted**: only Products used by no Dish or Meal can be deleted (feature 001). Any Adjustment or tick it still has in any Week is removed with it.
- **Product unit changed**: allowed only on unused Products (feature 001). Any Adjustment it has is removed, because its amount was in the old unit. Its ticks are kept.
- **Product leaves the plan with no Adjustment**: its line disappears. If it comes back later in the same Week, its earlier tick comes back with it.
- **Meal moved between Weeks** (desktop drag and drop, later feature) or copied with "Skopiuj do następnego tygodnia": both Weeks' lists follow their own Meals. The target Week's Adjustments, Extras and ticks are left as they are (feature 002, FR-033).
- **A Product with a zero amount**: Ingredient amounts are always above zero (feature 001), so every planned Product contributes something.
- **Large Week**: 35 Meals over 100 distinct Products is a normal Week and must not feel slow (SC-002).
- **Very long names and Extras**: they wrap onto further lines rather than being cut off, and the amount stays readable.
- **Duplicate Extras**: allowed. "kawa" can be added twice; they are separate Extras.
- **An Extra with the same name as a Product item**: allowed. They are separate lines.
- **Offline**: everything in this feature works without a network, including sharing to apps on the device and copying to the clipboard.

## Requirements *(mandatory)*

### Functional Requirements

**The list**

- **FR-001**: The Lista zakupów tab MUST show the Shopping List of the Shown Week, replacing the current placeholder.
- **FR-002**: The tab MUST have its own Week header naming the Shown Week's dates (e.g. "16–22 lis 2026"), with ← / → buttons that show the previous and next Week. On phones, a horizontal swipe on the header MUST also change the Week: left for the next Week, right for the previous one, applied on release. The buttons stay visible on every screen size.
- **FR-003**: When the app starts, the Shown Week MUST be the Week containing today. While the app runs, the tab MUST keep its Shown Week when the user moves to other tabs and back. It MUST NOT follow or change the Week viewed in Tydzień.
- **FR-004**: The list MUST contain one Product item for each Product that has a Planned amount above zero in the Shown Week or has an Adjustment in the Shown Week, and one line for each Extra of the Shown Week.
- **FR-005**: The Planned amount of a Product MUST be the sum, over all Meals dated Monday to Sunday of the Shown Week, of that Product's Ingredient amount divided by the Meal's servings yield and multiplied by the Meal's Servings. For a Linked Meal the Ingredients and yield come from its Dish (including an Archived Dish); for a Detached Meal from its own copy.
- **FR-006**: The list MUST be live: any change to the Shown Week's Meals, to a Dish used by a Linked Meal in it, or to a Product, MUST be reflected the next time the list is visible, with no action from the user, and at once if the list is already on screen.
- **FR-007**: Each Product item MUST show the Product's name and its Total, formatted as in FR-008. When the Product has an Adjustment, the item MUST also show the Adjustment with its sign (e.g. "−500 g").
- **FR-008**: Totals MUST be formatted as follows, with a comma as the decimal separator:
  - g: below 1000 as whole grams ("750 g"); from 1000 as kg with up to 2 decimals and no trailing zeros ("1,25 kg").
  - ml: the same rule with ml and l.
  - pcs: rounded up to a whole number after the Adjustment, labelled "szt." ("3 szt.").
  - The kg or l switch uses the rounded value (999,6 g → "1 kg").
  - A Total above zero that rounds to 0 g or 0 ml shows as "1 g" or "1 ml".
- **FR-009**: A Product item whose Total is zero or below MUST stay on the list and be shown struck through, with its Adjustment visible.
- **FR-010**: The list MUST be sorted alphabetically by the text shown (Product name or Extra text), ignoring case and using Polish alphabetical order, with all ticked items below all unticked items and each part sorted the same way. Extras MUST be sorted together with Product items, not in a separate section.
- **FR-011**: When the Shown Week has no Product items and no Extras, the tab MUST show a short message that there is nothing to buy for this Week yet, and the field for adding Extras.

**Ticks**

- **FR-012**: Each List item MUST have a tick control that ticks or unticks it with one tap. Tapping the tick MUST NOT open the Adjustment sheet.
- **FR-013**: Ticks MUST be stored per Week: a Product item's tick belongs to that Product in that Week, and an Extra's tick to that Extra.
- **FR-014**: Ticks MUST be kept when the plan changes, including when a Product item's Total changes.

**Adjustments**

- **FR-015**: Tapping a Product item outside its tick control MUST open a sheet showing the Product's name, its Planned amount for the Shown Week, and a field for the Adjustment in the Product's unit, pre-filled with the current Adjustment if there is one.
- **FR-016**: The Adjustment field MUST accept a positive or negative number with up to 2 decimals (comma or dot as separator), stored rounded to 2 decimals. Saving MUST replace the Product's Adjustment for the Shown Week. Saving an empty field or 0 MUST remove the Adjustment.
- **FR-017**: Saving MUST be blocked, with the field pointed out, when its content is not a number.
- **FR-018**: A Product MUST have at most one Adjustment per Week. Adjustments MUST be kept when the plan changes, and MUST NOT affect any other Week.
- **FR-019**: Extras MUST NOT offer an Adjustment. Tapping an Extra outside its tick control does nothing.

**Extras**

- **FR-020**: The tab MUST offer a field for adding an Extra to the Shown Week. Confirming it MUST add an Extra with the typed text, trimmed of leading and trailing spaces, and clear the field. Empty or whitespace-only text MUST NOT add anything.
- **FR-021**: The user MUST be able to delete an Extra. Deleting MUST NOT ask for confirmation.
- **FR-022**: Extras MUST belong to one Week and MUST NOT be changed by plan changes or by "Skopiuj do następnego tygodnia".

**Sharing**

- **FR-023**: The tab MUST offer "Udostępnij listę" whenever the list has at least one item left to buy (FR-024).
- **FR-024**: "Udostępnij listę" MUST produce plain text: a first line naming the list and the Shown Week's dates, then one line per item left to buy, in the order shown on screen. Items left to buy are unticked Product items with a Total above zero and unticked Extras. Ticked and struck-through items MUST NOT be included. A Product item's line is its name and Total formatted as in FR-008, with no Adjustment shown; an Extra's line is its text.
- **FR-025**: The text MUST be passed to the device's share sheet where available. Otherwise it MUST be copied to the clipboard and a short message MUST confirm the copy. Cancelling the share sheet MUST NOT show an error.

**Interaction with other features**

- **FR-026**: Merging Product A into Product B (Produkty) MUST, in every Week, combine A's Adjustment with B's by adding them, and tick B only if both A and B were ticked in that Week. A's own Adjustments and ticks MUST then be removed.
- **FR-027**: Deleting a Product MUST remove its Adjustments and ticks in every Week.
- **FR-028**: Changing a Product's unit MUST remove its Adjustments in every Week, and keep its ticks.
- **FR-029**: "Skopiuj do następnego tygodnia" MUST continue to leave the next Week's Adjustments, Extras and ticks unchanged (feature 002, FR-033).

**General**

- **FR-030**: Adjustments, Extras and ticks MUST be stored on the device, survive closing and reopening the app, and work with no network.
- **FR-031**: All user-facing text MUST be in Polish. Framework7's own built-in labels stay as shipped.
- **FR-032**: On desktop (about 1024 px and wider) the tab MUST use the shared content column (feature 002, FR-041), and the Adjustment sheet MUST line up with it like the app's other sheets.

### Key Entities

- **Shopping List**: derived, never stored. For one Week: the Product items computed from that Week's Meals and Adjustments, plus that Week's Extras, each with its tick state.
- **Product item**: derived. A Product, its Planned amount, its Adjustment (if any), its Total and its tick state for the Week.
- **Adjustment**: stored. A Week, a Product and a signed amount in the Product's unit. At most one per Product per Week.
- **Extra**: stored. A Week, free text and a tick state. Has its own identity, so duplicates are separate.
- **Product tick**: stored. A Week and a Product that is ticked on that Week's list. Kept when the Product leaves the plan.
- **Week** (existing): identified by its Monday. Owns the three stored kinds above.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For a reference Week of at least 20 Meals (Linked and Detached, fractional Servings, a Product shared by several Dishes, every unit), 100% of the list's amounts match a hand calculation of the rules in FR-005 and FR-008.
- **SC-002**: With 35 Meals over 100 distinct Products in the Week and a year of Weeks stored, the list appears in under 300 ms after the tab is opened, as perceived by the user.
- **SC-003**: After any plan change in Tydzień, the list is correct the first time it is seen again, in 100% of cases, with no manual refresh, and every Adjustment, Extra and tick is unchanged.
- **SC-004**: Ticking an item takes one tap, and the user can tick a 30-item list in the shop without the list ever moving an unticked item out of the top part.
- **SC-005**: A shared list can be read by another person and turned into their own list by hand without asking what any line means: every line has a name and, for Product items, an amount with a unit.
- **SC-006**: After one online load, 100% of this feature's functions work in airplane mode, including after the app is closed and restarted.
- **SC-007**: No Adjustment, Extra or tick is ever lost or moved to another Week by plan changes, copying a Week, Product renames or app restarts.

## Assumptions

- **Feature scope**: this feature covers docs/SPEC.md's "Shopping List" section and the Lista zakupów screen: the live list, Adjustments, Extras, ticks, display rules and "Udostępnij listę". Goals and summaries, backup export/import and the desktop Tydzień grid stay in later features.
- **Simple Week swipe on the list**: the list's Week header changes Week when the swipe is released, like Tydzień before feature 003. The follow-the-finger gesture from feature 003 is not repeated here, because the list is not the app's primary navigation and its rows have their own swipe (deleting an Extra). The ← / → buttons stay visible on phones for the same reason.
- **No jump to today**: as in Tydzień, there is no "back to current Week" control. The list opens on the current Week at each app start (FR-003).
- **Adjustments only on listed Products**: an Adjustment is added by tapping a Product item, so it can only be set on a Product that is on the list. To buy something the plan doesn't use, the user adds an Extra. This keeps Extras as the only way to add items, as docs/SPEC.md describes.
- **An Adjustment replaces, it doesn't accumulate**: entering −500 g twice gives −500 g, not −1000 g. The sheet shows the current value, so editing it is direct.
- **Ticks are kept when amounts change**: docs/SPEC.md says checks are kept when the plan changes. A ticked item whose Total later grows stays ticked. The user is expected to notice it in the list.
- **Merging ticks conservatively**: after a Product merge, the joined line is ticked only if both were ticked, because an unticked line means something may still need buying.
- **Unit change drops Adjustments**: an Adjustment of −500 g makes no sense as −500 ml. This can only happen on an unused Product, so in practice it affects at most a leftover Adjustment.
- **No editing of Extras**: an Extra is deleted and added again to change it. docs/SPEC.md only asks for free-text items, and editing would add a sheet for a rare need.
- **No confirmation when deleting an Extra**: it is one line of text and quick to add again.
- **UI labels**: the Polish labels for the Adjustment sheet, the Extras field and the empty state are chosen in the plan's UI contract. If Adjustment or Extra get a UI name, it is added to GLOSSARY.md like "Produkt" and "Danie".
- **Backup**: backup export/import (a later feature) must include Adjustments, Extras and ticks, since they are user data that cannot be recomputed.
- **Phones and iPhone first**: checked on a real iPhone, as the installed app and in a Safari tab. The Android check stays deferred, as in feature 001.
- **Framework7 patterns**: the list, ticks, sheet, input and swipe-to-delete use Framework7's standard parts in the app's look (green accent, warm background, white cards).
